## 04. 갓 세이브 버밍엄 : 상호작용 연출


### 개발 과정

개발 #1 : 상호작용 연출 고도화

배경

상호작용 대상마다 시작 위치, 조작점의 높이와 재생할 동작이 달랐습니다. 대상 액터에 부착하는 컴포넌트로 위치·연출 데이터를 모듈화하고, 상황에 맞는 몽타주 선택 → 자동 접근 → 모션 워핑과 상체 틸트 보정으로 이어지는 실행 구조를 구성했습니다.

설계와 데이터 구성

상호작용의 공통 기능과 개별 처리 분리

상호작용 베이스 클래스에 대상·도구 조회와 몽타주 선택 등 반복되는 데이터 구성 기능을 모았습니다. 이를 상속한 파생 클래스는 채집·획득·문 열기처럼 각 상호작용에 필요한 데이터를 구성하고 결과를 처리합니다.

자동 접근, 선행 동작, 몽타주 재생과 자세 보정은 별도의 공통 실행 계층에서 순서대로 처리합니다. 파생 클래스가 전달한 몽타주·시간·접근·틸트 설정을 사용하므로, 새로운 상호작용을 추가할 때 실행 흐름을 반복해서 구현하지 않도록 구성했습니다.

데이터로 설정하는 상호작용 위치와 방향

게임 오브젝트에 상호작용 지점 컴포넌트를 여러 개 부착하고, 상호작용별 실행 위치와 방향을 설정할 수 있도록 구성했습니다. 해당 상호작용에 사용할 수 있는 지점 중 캐릭터와 수평 거리가 가장 가까운 지점을 선택하고, 별도 지점이 없으면 기본 위치를 사용하는 경로를 둡니다.

접근 거리와 도착 여유 범위, 몽타주의 워핑 목표 거리를 독립적으로 조정할 수 있게 해 콘텐츠 담당자가 오브젝트 배치와 상호작용 특성에 맞춰 연출을 설정하도록 했습니다.

구현 결과 : 태그·자세·높이 기반 몽타주 선택

- 도구·대상·상호작용의 추가 태그와 서기·앉기 자세로 모션 후보를 필터링합니다. 태그는 정확히 일치하는 조건으로 비교하며, 비워 둔 조건은 검사하지 않습니다.

- 대상의 조작점과 캐릭터 발바닥 사이의 상대 높이로 모션을 선택합니다. 조작점이 없으면 대상의 기준 위치를 사용합니다.

- 우선순위가 높은 후보를 먼저 선택하고, 같은 우선순위에서는 대상 높이를 수용하는 가장 작은 높이 상한을 선택합니다. 두 조건이 같으면 무작위 선택으로 동작을 분산합니다.

- 직접 지정한 몽타주를 우선 사용하고, 자동 매칭에 실패하면 대체 모션을 사용하도록 구성했습니다.

## 05. 갓 세이브 버밍엄 : 자동 접근


### 개발 과정

개발 #2 : 자동 접근과 이동 경로 처리

자동 접근의 경계와 워핑 위치

기본 접근 경계는 접근 거리와 도착 여유 범위를 더해 계산합니다. 캐릭터가 경계 안에 있으면 자동 이동을 생략하고, 밖에 있으면 접근을 실행합니다. 몽타주가 시작된 뒤에는 별도로 설정한 워핑 목표 거리로 위치를 정렬합니다.

이동 가능한 목적지를 선택하고 접근 결과 판정

1. 가장 가까운 유효 지점 선택 시도한 상호작용에 연결된 실행 지점 중 캐릭터와 수평 거리가 가장 가까운 곳을 선택합니다.

2. 두 목적지 후보 계산 실행 지점에서 캐릭터 방향으로 접근 거리만큼 떨어진 위치와 실행 지점 자체를 각각 NavMesh에 투영합니다. 투영된 두 위치 중 캐릭터와 직선 수평 거리가 짧은 쪽을 선택합니다.

3. 경계 밖에서만 자동 접근 접근 경계 밖에 있는 캐릭터를 선택한 목적지로 이동시킵니다. 후보가 벽이나 난간 밖에 놓여 투영 결과가 멀어지면 다른 후보를 사용할 수 있도록 구성했습니다.

4. 도착 범위에 들어온 뒤 연출 시작 목적지 좌표와의 정확한 일치보다 실행 지점의 도착 범위 진입을 기준으로 판정합니다. 이후 선행 동작과 본 동작을 순서대로 실행하고, 몽타주의 워핑 구간에서 목표 위치로 정렬합니다.

서버 경로 요청과 클라이언트 이동 처리

클라이언트는 선택한 목적지까지의 이동 경로(Path)를 서버에 요청합니다. 서버가 계산한 경로를 전달받으면, 클라이언트가 해당 Path를 따라 캐릭터의 이동을 처리합니다.

서버는 이동 방향, 거리 변화와 제한 시간으로 접근 실패를 검사해 상호작용을 취소합니다. 서버와 소유 클라이언트는 실행 지점의 도착 범위 진입을 판정하고, 도착 후 선행 동작과 본 동작을 시작합니다.

접근 경로·판정 범위·워핑 목표와 상체 틸트의 기준점을 디버그 도형으로 표시해 위치 계산과 자세 보정을 확인할 수 있도록 했습니다.

클라이언트 (목적지까지의 Path 요청) > 서버 (경로 계산 및 전달) > 클라이언트 (수신한 Path로 이동)

접근 거리와 도착 여유는 오브젝트별 설정값이며, 이동 목적지와 연출 시 워핑 목표는 구분합니다.

## 06. 갓 세이브 버밍엄 : 대상에 맞춘 연출


### 개발 과정

개발 #3 : 모션 워핑과 상체 자세 보정

세 Target Name과 몽타주 노티파이로 위치·회전 제어

자동 접근은 동작을 시작할 수 있는 범위까지 캐릭터를 이동시킵니다. 이후 공통 실행 계층은 Motion Warping에 세 목표를 각각의 Target Name으로 등록합니다.

- Interaction - 상호작용 스팟 위치

- Root - 대상 위치

- Handle - 대상의 Handle Component 위치

기획자는 몽타주에 MotionWarp 노티파이를 배치하고, 각 구간이 참조할 Target Name과 위치 보정·회전 보정 여부를 지정합니다. 한 타깃으로 위치만 이동하거나, Interaction으로 위치를 이동한 다음 별도 구간에서 Handle을 향해 회전하도록 구성할 수 있습니다.

타깃 등록은 목표 데이터를 제공하고, 실제 이동과 회전의 적용 시점은 몽타주의 노티파이 설정이 결정합니다. 대상 위치와 스팟 위치를 구분하므로 몽타주 연출에 맞는 목표를 선택할 수 있습니다.

대상 높이와 거리로 상체 틸트 계산

모션 선택은 발바닥 기준의 높이 구간을 판정하고, 상체 틸트는 자세별 상체 기준점에서 대상을 향하는 각도를 계산합니다. 높이 차이와 수평 거리로 보정 각도를 구하므로 대상 높이가 같아도 거리가 달라지면 자세가 달라집니다.

몽타주로 기본 동작을 선택하고 틸트로 연속적인 자세 보정을 더하도록 역할을 나눴습니다. 애니메이션 애셋 참조에서는 타입별 보정 포즈와 가산 블렌딩, 보정 강도를 조절하는 커브를 확인했습니다.

몽타주 노티파이 구성 예시

Interaction (첫 구간에서 위치 이동) > Handle (다음 구간에서 회전)

회전·위치 보정 여부와 Target Name을 구간마다 지정해 연출을 구성합니다.

상체 틸트의 기준

보정 각도 = atan2(대상 Z - 상체 기준점 Z, 수평 거리)

상체 기준점은 캡슐 중심에 자세별 오프셋을 더한 위치입니다. 서기·앉기 자세와 대상 위치를 반영해 연속적인 자세 보정을 더합니다.

## 07. 갓 세이브 버밍엄 : 저널 기능


### 개발 과정

개발 #4 : 저널 기능 구현

FlowGraph로 진행 조건을 제어하고, 컴포넌트에서 등록 상태를 관리하며, ViewModel과 위젯으로 카테고리별 목록·읽음 표시·등록 연출을 제공하는 저널 시스템을 구현했습니다.

진행 조건 (Flow / 게임 이벤트) > 등록 상태 (공유·개인 컴포넌트) > 화면 데이터 (ViewModel) > 목록과 연출 (위젯 / 연출 큐)

진행 조건과 저널 데이터 분리

카테고리·제목·본문·독백은 정적 데이터로 정의하고, 등록 상태와 읽음 여부는 실행 데이터로 분리했습니다. 초기화할 때 각 컴포넌트가 담당하는 카테고리의 저널 객체를 만들고 잠긴 상태로 시작하도록 구성했습니다.

저널 컴포넌트는 잠김·열림의 등록 상태를 관리하고 이후 진행 조건은 Flow 그래프에서 처리합니다. 게임 이벤트와 커스텀 Flow 노드를 연결해 기획자가 조건과 콘텐츠를 직접 수정할 수 있게 했습니다.

서버 권한 등록과 공유·개인 상태 동기화

Flow의 등록 요청을 실행 주체에 따라 공유 또는 개인 저널 컴포넌트로 전달했습니다. 서버에서 초기화 준비와 중복 등록 여부를 확인한 뒤 상태를 변경하고, 클라이언트에는 갱신된 등록 목록을 복제했습니다.

서버가 관리하는 원본과 네트워크 전달 목록을 분리하고, 초기화와 상태 반영이 공통 경로를 거치도록 구성했습니다. 이미 적용한 저널을 기록해 전체 목록이 반복 전달되더라도 중복 반영하지 않도록 했습니다.

공유·개인 저널의 카테고리와 복제 범위는 상속과 가상함수로 분리하고, 등록·초기화·목록 적용은 공통 컴포넌트에 유지했습니다.

등록 이벤트와 프레임 단위 연출 큐

게임플레이에 등록 사실을 알리는 이벤트, 화면에 신규 항목을 전달하는 이벤트, 기존 목록을 다시 반영하는 이벤트의 역할을 구분했습니다. 등록 사실은 Flow 진행 조건이나 후속 HUD 표시에도 연결했습니다.

같은 프레임에 등록된 저널은 하나의 묶음으로 모아 다음 프레임에 큐로 전달했습니다. 현재 연출이 진행 중이면 다음 묶음을 대기시키고, 연출이 가능한 시점에 순서대로 처리하도록 구성했습니다.

신규 등록 이벤트는 목록 추가와 팝업 연출 양쪽에서 사용하므로, 알림을 막기 위해 이벤트 자체를 차단하면 목록도 누락될 수 있습니다. 기존 상태의 목록 갱신은 별도 경로로 반영해 신규 등록 연출과 분리했습니다.

카테고리 목록·선택·읽음 표시의 UI 반영

컴포넌트의 객체를 화면에서 직접 공유하지 않고, 전달된 데이터로 UI 전용 객체를 구성했습니다. ViewModel에서 메인·서브·생존 목록을 분류하고 중복 추가를 방지하며, 최신 등록 항목이 먼저 보이도록 목록을 제공했습니다.

- 선택 항목과 마지막 선택 항목을 관리하고, 항목 선택 시 읽음 상태를 반영했습니다.

- 카테고리별 읽지 않은 항목의 존재 여부를 계산해 목록 아이콘과 함께 갱신했습니다.

- FieldNotify로 목록·선택·읽음 상태의 변화를 위젯에 전달했습니다.

- 카테고리 전환 시 선택과 스크롤을 정리하고, 화면 생성·제거 주기에 맞춰 이벤트 연결과 데이터 정리를 수행했습니다.

## 08. 갓 세이브 버밍엄 : 저장과 복원


### 개발 과정

개발 #5 : 세이브·로드와 재접속

저널 기능 구현에 더해 플러그인 실행 상태를 기존 저장 시스템에 통합하고, 복원된 상태와 신규 등록을 구분하는 흐름을 설계했습니다.

게임 데이터 | 플러그인 실행 상태
GameState / PlayerState의 저널 컴포넌트 | UFlowSaveGame
기존 객체 직렬화 경로에 통합 | 메모리 바이너리로 변환해 별도 섹션에 통합

원본 Flow 애셋의 비동기 로딩과 소유자 준비가 모두 완료된 뒤, 저장된 진행 상태를 복원하고 Flow를 실행합니다.

기존 저장 시스템에 Flow 실행 상태 통합

Unreal Engine C++ 기반으로 저널의 세이브·로드를 설계하고 구현했습니다. GameState의 공유 저널과 PlayerState의 개인 저널 컴포넌트는 기존 직렬화 경로를 활용하고, 플러그인의 진행 상태는 별도 저장 섹션으로 분리했습니다.

- FlowGraph의 UFlowSaveGame을 메모리 바이너리로 변환해 세이브 파일에 저장했습니다.

- 저장된 실행 인스턴스에 맞는 원본 애셋을 찾아 로드하고 진행 상태를 복원할 수 있도록, FSoftObjectPath와 TMap으로 애셋 경로와 인스턴스 이름을 관리했습니다.

- 개인 저널은 플레이어 ID로 구분해 각 플레이어의 진행 상태를 복원하도록 구성했습니다.

애셋과 소유자 준비 이후에 실행 상태 복원

저장 데이터를 읽는 시점과 Flow를 실행할 수 있는 시점을 분리했습니다. 로드 시 원본 Flow 애셋의 비동기 로딩 완료와 소유자 준비 상태를 함께 확인해 실행 시점을 제어했습니다.

애셋 경로, 실행 인스턴스와 플레이어별 저장 데이터를 연결해 복원 대상과 실행 주체가 준비된 이후 진행 상태를 적용하도록 구현했습니다.

클라이언트별 초기 저널 등록

서버에서 직렬화를 마친 개인 저널 초기 목록을 Client RPC로 전달해, 플레이어별로 저장된 저널 상태를 클라이언트에 반영했습니다.

바이너리 분석으로 저장 구조 불일치 추적

문제

저장 데이터 구조와 읽기 순서가 일치하지 않아 로딩 지연이 발생했습니다.

분석과 개선

구간별 시간을 측정하고 바이너리 데이터를 분석해, 누락된 저장 섹션으로 인해 이후 데이터를 잘못 해석하는 지점을 확인했습니다. 저널 데이터가 없는 경우에도 저장 구조를 유지하도록 개선했습니다.

## 09. 갓 세이브 버밍엄 : 게임 플로우 / UI


### 개발 과정

개발 #6 : 게임 플로우와 UI 매니저

타이틀부터 플레이 종료까지 이어지는 흐름

타이틀 화면 → 로딩 화면 → 인게임 → 플레이 종료 및 타이틀 복귀로 이어지는 게임 플로우를 구현했습니다. 이 흐름에서 화면의 표시 순서와 입력 포커스, 위젯의 생성·재사용을 일관되게 관리하기 위해 데이터 기반 UI 매니저를 설계했습니다.

타이틀 (메뉴 / UV 패닝) > 로딩 (Slate / MoviePlayer) > 인게임 (HUD / 팝업 / 상태창) > 종료 (타이틀 화면 복귀)

로딩 화면에서 Slate와 MoviePlayer를 선택한 이유

맵 전환의 동기 로딩으로 게임 스레드가 블로킹되는 구간에서는 일반 UMG 위젯의 Tick과 애니메이션 갱신에 의존한 연출이 진행되지 않습니다. 로딩 화면은 이 갱신 경로에 의존하지 않도록 Slate 위젯으로 구성하고 MoviePlayer에 연결했습니다. 게임 스레드가 로딩을 처리하는 동안에도 MoviePlayer의 별도 로딩 화면 갱신 경로를 통해 연출이 이어지도록 구현했습니다.

타이틀·인게임 UI와 로딩 UI의 실행 환경을 구분해 기술을 선택했습니다. 타이틀 배경은 텍스처 UV를 이동하는 방식으로 패닝을 구현하고, 베지어 곡선을 적용해 부드럽게 움직이도록 했습니다.

게임 플로우를 지원하는 데이터 기반 UI 매니저

UGameInstanceSubsystem 기반 UI 매니저에서 타이틀·인게임 화면의 출력과 상태를 관리했습니다. 위젯 클래스와 레이어 정보를 Data Table로 관리하고, Layer / Stack 구조로 Z-Order와 입력 포커스를 제어했습니다. 인벤토리·HUD 팝업의 열림·닫힘과 상호 배타적인 표시 상태도 이 구조에서 처리했습니다.

- Soft Reference 비동기 로딩과 위젯 풀링으로 반복적인 생성 비용을 줄였습니다.

- 사용 중인 위젯은 TWeakObjectPtr, 대기 중인 위젯은 TObjectPtr로 관리해 화면 해제와 캐시 유지에 맞게 참조 수명을 분리했습니다.

- 재사용 시 초기화가 반복되지 않는 위젯 특성을 고려해 화면 생성·해제 주기에 맞춰 Delegate를 연결하고 해제하도록 변경했습니다.

- Unreal Insights로 인벤토리 갱신 구간의 프레임 저하를 추적했습니다. Scroll Box에서 위젯 캐시가 초기화되고 다시 그려지며 발생하던 히치를 List View 구조로 변경해 해결했습니다.

- 상태창 스탯과 저널을 MVVM으로 연결하고, 인벤토리 정렬 기준을 Config로 분리했습니다.

## 12. Project : Zero Sector

팀 프로젝트 / 5명 / 팀장

좀비와 전투하고 NPC의 대화와 단서를 통해 백신 개발자를 찾는 추리 FPS

플랫폼 | Windows
개발 환경 | UE 5.4 · C++
개발 기간 | 2025.03.11 ~ 2025.06.09


### 구현 결과

NPC별 대화 데이터 | 선택에 따라 달라지는 면담 | 1인칭 전투

필요한 데이터만 로드하고, 컴포넌트의 의존성을 줄였습니다.

담당 범위: 팀장 · Git 프로젝트 관리 · UI(작전판, HUD, 강화판 제외)와 단서 데이터 관리 로직을 제외한 게임 요소의 C++ 개발

- NPC 식별자와 Soft Reference 경로를 TMap으로 연결해 해당 NPC에 필요한 대화 테이블만 런타임에 로드했습니다.

- 캐릭터에서 컴포넌트의 Delegate와 함수를 연결하는 중재자 구조로 컴포넌트 간 직접 참조를 줄였습니다.

- Git trunk-based 전략을 적용하고 브랜치와 병합을 관리하며 팀의 기능 구현을 조율했습니다.


### 회고

상속 기반 무기에서 데이터 기반 무기로

기반 클래스에 총기의 공통 기능을 두고 파생 클래스로 각 총기를 구현했습니다. 무기가 늘 때마다 클래스가 필요해지는 한계를 경험했고, 이후 Black Space에서는 Data Asset 교체로 무기를 확장하는 구조로 발전시켰습니다.

## 13. Project : No-Face

팀 프로젝트 / 4명 / 팀장

절차적으로 생성되는 맵에서 다양한 무기와 스킬로 전투하는 쿼터뷰 로그라이크

플랫폼 | Windows
개발 환경 | UE 5.4 · C++
개발 기간 | 2024.09.06 ~ 2024.12.04


### 구현 결과

무기별 전투 | 지역 타겟팅 스킬 | 보스 전투

준비와 실행을 분리한 지역 타겟팅 스킬

담당 범위: 팀장 · Git 프로젝트 관리 · PCG 맵 생성 알고리즘을 제외한 게임 요소의 C++ 개발

- TFunction과 람다로 스킬 동작을 감싸 TQueue에 보관하고, 타겟팅 준비 후 공격 입력에 맞춰 실행했습니다.

- Motion Warping으로 자연스러운 회피 이동을 구현하고, 무기 타입에 따라 애니메이션과 이동 속도를 변경했습니다.

- 팀의 진행 상황과 의견을 조율하고 Git 기반으로 협업하며 프로젝트를 완성했습니다.


### 회고

스킬 시스템의 확장성에 대한 회고

스킬을 함수로 구현하면서 기능이 늘수록 코드가 커지고 수정 복잡도가 증가하는 한계를 확인했습니다. 후속 설계에서는 공통 실행과 큐 처리를 담당하는 범용 구조를 두고, 데미지·범위·이펙트를 데이터로 분리하는 방향이 좋을 것 같다는 생각을 하였습니다.
