01상호작용 연출과 서버·클라이언트 역할 분리SceneComponent · Server RPC · Data Table

문제와 설계

상호작용 대상마다 시작 위치, 높이 차이와 몽타주가 달랐고, 기존 싱글플레이 로직을 멀티플레이에서도 사용할 수 있어야 했습니다. 대상 액터에 부착하는 커스텀 SceneComponent로 위치와 연출 데이터를 모듈화했습니다.

구현

  • Server RPC로 유효한 이동 경로를 확인하고 반환받은 경로에 따라 클라이언트가 이동을 실행하도록 역할을 분리했습니다.
  • 캐릭터 상태, 대상 태그와 높이 차이를 바탕으로 Data Table에서 상황에 맞는 몽타주를 선택했습니다.
  • Replication과 Client / Server / Multicast RPC로 서버와 클라이언트의 실행 로직을 분리했습니다.

  • Subsystem에 게임 이벤트 Delegate를 모으고, 해당 이벤트를 받아 저널이 진행되도록 연결했습니다.
  • 커스텀 Flow Node와 AddOn, Data Table / Registry로 콘텐츠 확장과 데이터 수정을 지원했습니다.

로딩 화면에서 Slate와 MoviePlayer를 선택한 이유

맵 전환의 동기 로딩으로 게임 스레드가 블로킹되는 구간에서는 일반 UMG 위젯의 Tick과 애니메이션 갱신에 의존한 연출이 진행되지 않습니다. 로딩 화면은 이 갱신 경로에 의존하지 않도록 Slate 위젯으로 구성하고 MoviePlayer에 연결했습니다. 게임 스레드가 로딩을 처리하는 동안에도 MoviePlayer의 별도 로딩 화면 갱신 경로를 통해 연출이 이어지도록 구현했습니다.

타이틀·인게임 UI와 로딩 UI의 실행 환경을 구분해 기술을 선택했으며, 타이틀 배경의 부드러운 패닝에는 베지어 곡선을 적용했습니다.

게임 플로우를 지원하는 데이터 기반 UI 매니저

UGameInstanceSubsystem 기반 UI 매니저에서 타이틀·인게임 화면의 출력과 상태를 관리했습니다. 위젯 클래스와 레이어 정보를 Data Table로 관리하고, Layer / Stack 구조로 Z-Order와 입력 포커스를 제어했습니다. 로그창·인벤토리·HUD 팝업의 열림·닫힘과 상호 배타적인 표시 상태도 이 구조에서 처리했습니다.

  • Soft Reference 비동기 로딩과 위젯 풀링으로 반복적인 생성 비용을 줄였습니다.
  • 사용 중인 위젯은 TWeakObjectPtr, 대기 중인 위젯은 TObjectPtr로 관리해 화면 해제와 캐시 유지에 맞게 참조 수명을 분리했습니다.
  • 재사용 시 Initialize가 다시 호출되지 않는 특성을 고려해 Construct / Destruct에서 Delegate를 바인딩·해제하도록 변경했습니다.
  • 아이템 수가 많을 때 히치가 발생하던 인벤토리를 Scroll Box에서 List View 구조로 변경했습니다.
  • 상태창 스탯과 저널을 MVVM으로 연결하고, 인벤토리 정렬 기준을 Config로 분리했습니다.

문제에서 구현까지

01기존 저장 시스템에 Flow 실행 상태 통합FStructuredArchive · UFlowSaveGame · 메모리 직렬화

Unreal Engine C++ 기반으로 저널의 세이브·로드를 설계하고 구현했습니다. GameState의 공유 저널과 PlayerState의 개인 저널 컴포넌트는 기존 직렬화 경로를 활용하고, 플러그인의 실행 진행 상태는 JournalFlow 저장 섹션으로 분리했습니다.

  • FlowGraph의 UFlowSaveGame을 메모리 바이너리로 변환해 기존 세이브 파일에 저장했습니다.
  • FSoftObjectPath와 TMap으로 원본 애셋 경로와 실행 인스턴스 이름을 연결했습니다.
  • 개인 저널은 플레이어 ID로 구분해 각 플레이어의 진행 상태를 복원하도록 구성했습니다.
02애셋과 소유자 준비 이후에 실행 상태 복원AssetManager · 비동기 로딩 · 소유자 준비 상태

저장 데이터를 읽는 시점과 Flow를 실행할 수 있는 시점을 분리했습니다. 로드 시 원본 Flow 애셋의 비동기 로딩 완료와 소유자 준비 상태를 함께 확인해 실행 시점을 제어했습니다.

애셋 경로, 실행 인스턴스와 플레이어별 저장 데이터를 연결해 복원 대상과 실행 주체가 준비된 이후 진행 상태를 적용하도록 구현했습니다.

03재접속 초기 상태와 신규 등록 연출 분리Replication · RepNotify · Client RPC · COND_OwnerOnly

문제

재접속 시 복제된 기존 저널이 신규 등록으로 인식돼 알림이 다시 출력되는 문제가 있었습니다. 프로퍼티 복제와 RPC의 도착 순서를 전제하지 않는 초기화 구조가 필요했습니다.

구현

  • 서버가 확정한 개인 저널 초기 목록을 Client RPC로 전달했습니다.
  • 복제와 RPC 중 어느 것이 먼저 도착하더라도 초기 목록을 확보한 뒤 신규 등록 연출 여부를 판정하도록 구성했습니다.
  • 개인 저널 목록에는 COND_OwnerOnly를 적용해 소유 클라이언트에게만 복제했습니다.
  • 공유·개인 저널의 초기화는 상속과 가상함수로 분리하고, 공통 상태 반영 로직은 Base 컴포넌트에 유지했습니다.
  • MVVM과 Delegate로 저널 상태 변경과 UI 갱신을 연결했습니다.
구현·검증 범위

초기 상태 동기화와 신규 등록 판정을 분리하는 구조를 구현했습니다. 확인된 UI 부수 효과는 후속 검증 대상으로 남아 있습니다.
